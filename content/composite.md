:::brief 評価軸を分け、重み付けはコードで決める
- **範囲をそろえる。** 段階数の違うScoreを、そのまま足しません。
- **意味を残す。** 合成値は並べ替え用の指標で、好まれる確率ではありません。
- **必須条件は別。** 「歌詞なし」などを、高得点との平均で相殺しません。
:::

条件で絞る | 満たす必要がある制約を先に確認
軸ごとに評価 | 各Scoreの範囲をそろえる
重み付けする | コードで合成して候補を並べる
! 音楽推薦を考える設計例です。効果を実証した機能ではありません。
:::

## 「総合的におすすめ」を分解する
- 曲の候補を並べ替える場面を、教材として考えます。
- 「この曲はおすすめか」だけでは、何を優先したのか分かりません。
- 曲の説明文を材料として、作業を邪魔しにくいという記述、気分との適合などを別々に評価する設計が考えられます。
- これは実証済みの音楽推薦機能ではなく、応用を考える練習です。

公式のComposite scoringは、複数の評価軸を分け、コードで重み付けして合成するパターンです。[公式：Composite scoring](https://docs.typesafe.ai/patterns/composite-scoring)

## 範囲をそろえる
3段階のScoreは0〜2、5段階は0〜4です。そのまま足すと、基準の段階数だけで影響が変わります。以下は、0〜2の2つのScoreを0〜1にそろえる教材です。

```js
// 各scoreは3段階（0〜2）で設計した場合。
const focusFit = answers.focus_fit.score / 2;
const moodFit = answers.mood_fit.score / 2;

// 重みは説明用であり、評価で最適化した値ではない。
const rankingScore = 0.7 * focusFit + 0.3 * moodFit;
```

0.7と0.3は、人が設定した優先順位です。「AIが0.82と言った」だけでなく、どの判断を何割使ったのかが分かる構成になります。

## 合成値を「確率」と呼ばない
たとえば合成値が0.82でも、ユーザーが82%の確率で気に入ると実証されたわけではありません。この教材では`rankingScore`という名前にし、候補を並べ替えるための独自指標として扱います。

## 不確かな評価を混ぜたらどうするか
- 片方の回答が不確かなら、単純に高い合成値だけ見て採用しないようにします。
- 本ガイドの設計例では、必要な軸のconfidenceが条件を満たさない場合、元のルールベースの並び順に戻します。
- 必ず全軸の最低値を採用すべきという意味ではなく、採用条件も要件として定義するということです。

## 平均と条件判定を混同しない
「歌詞なしが必須」という条件を、他の高得点と平均して相殺するのは不適切です。必須条件は先にフィルターし、その後に残った候補を並べます。重みで調整する好みと、満たす必要のある制約を分けてください。

:::answer 確認問題：重み付きスコアが0.9なら、正解確率90%として表示してよいですか？
そのような検証をしていない限り、表示できません。独自に合成した並べ替えの指標と、確率として較正された値は別です。
:::
