## 同じ文章を、いくつかの角度から読む
問い合わせの「主な用件」と「不満の強さ」は、同じ文章から判断できます。最初の答えを待ってから2つ目を聞かなくてもよい場合は、1つの`questions`にまとめます。各質問は同じStateに対して独立に評価されます。[公式：Primitives](https://docs.typesafe.ai/primitives)

```json
{
  "model": "jev-1.13.0",
  "state": "保存が毎回失敗します。今日も登録できず困っています。",
  "questions": {
    "category": {
      "type": "choice",
      "instructions": "主な用件を選んでください。",
      "criteria": {
        "bug": "操作の失敗やエラーの報告",
        "question": "使い方の質問",
        "other": "上記以外、または不明"
      }
    },
    "frustration": {
      "type": "score",
      "instructions": "表現されている不満の強さはどの段階ですか？",
      "criteria": ["不満を表していない", "不満を表している", "強い怒りを表している"]
    }
  }
}
```

これは教材用の入力です。質問同士が互いの答えを読んでいるわけではありません。「categoryがbugだった場合だけ重大さを判断する」という条件は、返答後にコードで適用します。

## 先に聞き、後で使うか決める
この考え方を公式はSpeculative fan-outとして紹介しています。ある分岐でしか必要にならない判断もまとめて聞き、実際に必要な場合だけ利用します。[公式：Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out)

たとえば分類が機能要望だった場合、不具合の影響度という回答は使わない、という設計です。不必要な回答を「何か返ったから」と無理に表示しないことが重要です。

## まとめられない場合
質問Bが、質問Aの答えを材料として本当に必要とするなら、同じリクエスト内で順番に依存させることはできません。コードでAの結果を確認し、必要な材料を取得してからBを呼ぶ、という別段階にします。

## まとめれば何でも無料、ではない
Stateの繰り返し送信を減らせる一方、質問自体にも入力トークンが必要です。モデルの入力上限や質問の必要性を確認します。公式の並列質問の実験結果を、あらゆる用途で同じ倍率になる保証とは扱いません。[公式：Parallel questions](https://docs.typesafe.ai/cookbooks/parallel_questions) / [公式：Models](https://docs.typesafe.ai/models)

:::answer 確認問題：同じリクエストの質問Bに「質問Aの答えを見て」と書けば、Aの結果を使えますか？
その前提で設計してはいけません。質問は独立に評価されます。Aの結果に依存する処理は、コードで次の段階へ渡します。
:::
