## Stateは会話履歴ではなく、今回の判断材料
Stateは、今回のリクエストでJevに評価させる内容です。文字列だけでなく、JSONオブジェクトや配列も使えます。1つのリクエスト内の各質問は、同じStateをそれぞれ独立して参照します。[公式：State](https://docs.typesafe.ai/concepts/state)

最初は問い合わせ本文の文字列だけで十分です。「誰の発言を評価するのか」「直前にどのような操作をしたか」が必要になったら、名前を付けて分けます。

```json
{
  "ticket": {
    "message": "保存ボタンを押しても予定が増えません。",
    "screen": "予定の新規登録画面"
  },
  "known_context": {
    "save_requires_login": true
  }
}
```

このJSONは独自の教材です。認証が必要かという条件をJevに推測させず、アプリケーションが知っている事実として渡しています。ただし、実際の認証チェックそのものはサーバー側のコードが行います。

## 何を読んでほしいかを指す
- 構造が大きくなったら、質問文で対象のフィールドを指定します。
- たとえば「`ticket.message`の主な用件を分類してください」と書きます。
- 公式は、バッククォートで囲んだパスを使って対象を明確にする例を示しています。 [公式：How to build with TypeSafe](https://docs.typesafe.ai/concepts/how-to-build-with-system-one)

バッククォートは魔法のAPI構文ではありません。ここでは、自然言語の指示が何を指しているかを明確にする書き方として使います。

## 「全部渡せば正確」は成り立たない
過去の全問い合わせ、無関係なプロフィール、全商品の情報を毎回渡すと、必要な情報が埋もれます。公式も、無関係な内容が多いStateでは精度が下がると説明しています。[公式：Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

この教材では、判断したい文章と、その判断に不可欠な補足だけに絞ります。「あると便利そう」ではなく、「これがないと何を判断できないか」を基準にすると整理しやすくなります。

## 情報がない場合も表現する
- 「ログイン状態が不明」と「ログインしていない」は別です。
- 情報が欠けているのに`false`を入れると、モデルには否定の事実として見えてしまいます。
- 本ガイドの設計例では、不明な項目は省くか、`"unknown"`のように意味を明記します。
- DBの実際の値と、表示用の説明を混同しないでください。

:::answer 確認問題：問い合わせの分類にユーザーのメールアドレスは必要ですか？
通常の分類という教材の前提では必要ありません。文章の意味に関係しない個人情報は、送信する材料に含めない設計にします。
:::
