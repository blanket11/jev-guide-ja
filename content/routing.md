## 「何をするか」と「今してよいか」
たとえば、問い合わせが使い方の質問に分類されたら、関連ヘルプの候補を出します。ただし分類が不確かなら、自動で1つに決めず、管理者に確認してもらいます。分類結果と不確実性を2つの軸で使うパターンが、公式のConfidence-gated routingです。[公式：Confidence-gated routing](https://docs.typesafe.ai/patterns/confidence-routing)

## まずは副作用の小さい処理で
以下は、本ガイド独自の学習用コードです。0.85は仮の境界です。実際の正解データで決めた値ではありません。データの更新や通知の送信は行わず、次の処理の候補だけを返します。

```js
function planRoute(answer) {
  if (answer.confidence < 0.85) {
    return { kind: "review", reason: "uncertain" };
  }
  if (answer.choice === "how_to") {
    return { kind: "suggest_help" };
  }
  if (answer.choice === "bug") {
    return { kind: "suggest_bug_label" };
  }
  return { kind: "review", reason: "other_category" };
}
```

この段階で表示したいのは「削除しました」ではなく、「この候補でよいか」です。AIの結果が間違っても戻せる設計を、最初の導入範囲にします。

## 文章生成モデルと組み合わせる
内容を分類し、ヘルプの照会はコード、説明文が必要なケースは文章生成モデル、判断が難しいものは人へ回す、という構成もあります。Jev自体が返信文を書くわけではありません。振り分けと実処理は自分のアプリケーションが制御します。[公式：Intent routing](https://docs.typesafe.ai/patterns/intent-routing)

## 既存の安全な経路を残す
Jevのリクエストが失敗したら、従来の受付や検索に戻す設計を考えます。「AIに接続できないため、お問い合わせそのものが消える」という依存は作りません。新しい判断部分を外してもサービスの主要機能が動く構成を、教材の出発点にします。

## 認可は別の条件
分類が高いconfidenceで「予定の削除」になっても、そのユーザーがその予定を削除してよいかは別の問題です。認証済みユーザー、対象データの所有権、取り消せるか、ユーザーの確認といった条件を、サーバー側で検証します。

:::answer 確認問題：「confidenceが0.99ならユーザー確認なしで削除」を安全な一般ルールにできますか？
できません。しきい値は権限や明示的な意思確認の代わりになりません。どの処理か、誤った場合の影響は何かを、別に設計します。
:::
