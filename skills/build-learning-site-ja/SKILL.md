# 日本語のブロック型学習サイトを作る

**情報を削って簡単に見せるのではなく、理解できる単位に分ける。**
対象はJevに限らない。技術・ツール・業務知識など、依頼されたテーマに置き換える。
前の会話を読めなくても、このフォルダーだけで作業を進める。

## 最初に読むもの

- 調査・構成・執筆前に [記事設計](references/editorial.md) を読む。
- 実装・検証・公開前に [実装と検証](references/implementation.md) を読む。
- 章の雛形には [章テンプレート](assets/chapter-template.md) を使う。
- 原典・確認日・未確認点は [調査台帳](assets/source-log-template.json) を複製して管理する。

## 1. 依頼範囲と既存環境を確認する

- 読者、学習テーマ、到達点、対象バージョン、公開先を整理する。曖昧なら一般的な前提を明記して進める。
- 権限・公開範囲・秘密情報・破壊的変更に関わる不明点は推測しない。
- 既存サイトではAGENTS.md、記事・出典・目次、ビルド、テスト、URL構成、デザインを読む。
- 既存のフレームワーク、URL、アンカー、コード例、検索、読了記録を不用意に置き換えない。
- 新規サイトでも30章に固定しない。前提知識と必要範囲から章数を決める。
- 依頼が制作なら提案だけで終わらず、実装・確認まで進める。公開は別の許可が必要な外部操作として扱う。

## 2. 一次資料から調べ、根拠を残す

- 公式ドキュメント、公式リポジトリ、規格原文などを読む。ユーザーの資料が対象なら、その資料を先に読む。
- 目次や索引で範囲を把握し、必要なページを実際に取得する。検索抜粋だけで実装仕様を決めない。
- API、SDK、モデル、料金、制限、サポート言語などの変動情報は現在の原典で確認する。
- 主張ごとの参照URL・節、読んだ日、バージョン、未確認点を記録する。
- 原典で確認した事実、教材としての説明、独自例、仮定、未検証、実測を分ける。
- 元資料の長い翻訳転載ではなく、独自の説明と例を作る。原典を読みたい人へのリンクを置く。
- 非公式教材には非公式・非公認を明示し、監修・提携を示唆しない。
- 読みやすさだけを修正した場合、仕様確認日は更新しない。

## 3. 入門から応用への学習順を作る

基本順序は「何に役立つか → 小さく試す → 概念を整理 → 実装 → 応用 → 検証・運用」。
非技術テーマでは「実装」を「実践・演習」に読み替える。

- 各章に「前提」と「読み終えたらできること」を1つずつ置く。
- 共通の小さな架空例を使い回し、毎章の状況理解をやり直させない。
- 用語を使う前に説明する。専門用語一覧を読破してから始める構成にしない。
- 応用は知識の紹介だけでなく、使いどころ、入力、判断、結果の扱い、失敗時の戻し方まで説明する。
- 未確定の仕様は作り話で埋めず、範囲を狭めるか未確認として残す。

## 4. 章を理解できるブロックにする

原則として「先に3つの要点 → 関係が分かる図解 → 見出しごとの本文 → 確認問題」。
用語集・索引・出典一覧などには、意味のない図を数合わせで入れない。

- 要点は結論を3項目で示す。見出しには「概要」より「何がどうなるか」を書く。
- 1ブロック1論点。短い導入、2〜4項目の箇条書き、必要な補足を組み合わせる。
- 箇条書きも意味の通る文にする。条件、例外、否定、単位、未検証の注意を削らない。
- 文の因果関係は短い文章でつなぐ。全文を機械的に箇条書きにしない。
- 手順には順番を、比較には共通の比較軸を、分岐には条件と各結果を示す。
- 図のノードにも具体的な内容を入れる。「入力→処理→出力」だけの装飾図で済ませない。
- 図は選択・読み上げできるHTMLテキストを基本にし、狭い画面で縦に並べる。
- 注意点、秘密情報、課金、破壊的操作の説明は折りたたまない。確認問題の答えは開閉してよい。
- コードは全文を隠さず、前に目的と実行場所、後に結果の読み方を書く。

## 5. サイトを実装する

- 既存の構成があればそれを保つ。新規は静的配信できる保守しやすい構成を選ぶ。
- 学習順ナビ、現在位置、章内目次、前後リンク、日本語検索、コードコピー、モバイル表示を用意する。
- 読了保存やテーマ切替を設ける場合、保存が禁止されたブラウザーでも本文やナビを壊さない。
- APIキー、業務秘密、実ユーザーのデータを公開HTML・JavaScript・教材へ含めない。
- 教材内デモは原則ローカルの固定データまたは計算とし、実API結果と明確に区別する。
- 実API通信は利用者が許可したサーバー／ローカル実習に分離し、費用・権限・送信内容を説明する。
- `:::brief`等はこの教材の独自構文。選んだ生成器で対応を実装するか、同等のコンポーネントに変換する。
- ux-writing、natural-japanese、ui-verification等が利用可能なら適切な役割で併用する。未導入を導入済みと扱わない。

## 6. 事実・表示・操作を別々に検証する

- 原典との突合、仮定と実測の区別、初心者の読み順を人間が追える形で再確認する。
- `python3 <このスキルのパス>/scripts/audit_content.py <記事ディレクトリ>` を補助チェックに使う。
- この監査は独自Markdown構文向けである。他形式には対応する検査を用意し、通過だけで正確さを保証しない。
- 既存章を再構成したらコードとリンクの差分を確認する。意図した仕様変更と編集変更を混同しない。
- プロジェクトのテスト・ビルドを実行し、全章のリンク切れと参照ファイルの存在を確認する。
- ブラウザーでPCとスマートフォンを確認する。横はみ出し、検索、メニュー、コピー、確認問題、デモを実際に操作する。
- 実行できなかった検査を成功と報告しない。テスト件数は実際の結果から記録する。

## 7. 許可された範囲で公開し、状態を伝える

- GitHubへの保存、Pagesの設定、Actions成功、公開URLでの表示確認を別々に扱う。
- 新規リポジトリではPagesのSourceがGitHub Actionsになっていることを確認する。
- 設定取得の404では公開元と権限を調べる。同じ再実行を繰り返させない。
- 既存の最新HEADを確認して変更する。force push、無断上書き、権限拡大をしない。
- 公開URL、変更点、確認済みの範囲、未検証の範囲を短く報告する。
- API・SDKを未実行なのに実行済みと書かない。ローカル表示だけで本番表示確認済みと書かない。
