# 実装・検証・公開

## コンテンツと表示を分離する

本文、章の順序・到達点などのメタデータ、出典、デザインを別に管理する。
元サイトではMarkdown、manifest、sources、静的ビルドという構成だったが、他の生成器でもよい。
既存環境を優先し、新規でも目的に対して過大な依存を追加しない。
このスキルは完成済みの汎用サイトエンジンではなく、制作手順と教材テンプレートを提供する。

章テンプレートの`:::brief`、`:::flow`、`:::cards`、`:::tip`、`:::warning`、`:::answer`は独自構文。
汎用Markdownでそのまま表示できると仮定しない。対応を実装するか、選んだ生成器の機能へ変換する。
コード内やリンク内の`|`を壊さないよう構文を扱い、コードとラベルは適切にエスケープする。

## 表示の初期目安

以下は今回の制作方針に由来する初期値で、普遍的な基準ではない。

- 日本語は読み慣れたゴシック系のシステムフォントを基本にする。
- 本文は16〜18px程度、行高は1.7〜1.9程度から確認する。
- 本文の読み幅は38〜46em程度を目安にし、極端に長い行を避ける。
- 見出しの前後とブロック間に余白を作り、同じ階層の見た目を統一する。
- コードは内部で横スクロールさせ、ページ全体をはみ出させない。

同じ内容の「要点」「ポイント」「まとめ」を何度も重ねない。
カードの枠や色を増やすだけで視覚的な区切りを作らない。
色だけで注意・成功・失敗を伝えない。
動きは最小限にして、キーボード操作、フォーカス表示、見出し階層、読み順を確認する。

## 必要な機能

学習順と現在位置、章内目次、前後リンク、検索、コードコピー、モバイル用ナビを優先する。
用語集・公式参照・確認日・訂正導線も置く。
読了記録やテーマはローカル保存が失敗しても利用を続けられるようにする。
スマートフォンの図解は縦に並べ、関係性と読む順番を保つ。

## デモと実習を分ける

公開する静的サイトは、原則としてAPIキーや外部推論なしで読めるようにする。
固定レスポンスには常に「説明用の仮データ」「実API未実行」等を表示する。
外部APIを使う実習は、別のサーバーまたはローカルコードと環境変数で扱う。
通信先、費用、送信データ、タイムアウト、失敗時の扱いを説明する。
例に実ユーザー・顧客・社内の秘密情報を使わない。

## 検証ゲート

### 根拠

原典の該当節が主張を支えるか、古い仕様が混じっていないか、説明用の仮定が明示されているかを確認する。
出典が存在することと、出典がその主張を支えることを別に確認する。

### コンテンツ

独自構文を使う記事には同梱の`audit_content.py`を実行する。
長い段落等の警告は判断材料であり、文字数を満たすための削除をしない。
索引・用語集などを対象にしないよう、必要な記事ファイルを選ぶか`--exclude`を指定する。
再構成では元のコードブロックとリンク先の集合も比較し、変更理由を確認する。

### 機能

テストとビルドを実行する。
内部リンク、章数、ファイル・アンカー、コードの表示とコピー、検索、デモ、開閉、テーマを検査する。
保存を禁止した状態でも本文と操作が壊れないか確認する。
既存サイトのテスト件数を、新しいサイトのテスト結果として流用しない。

### 見た目

PC 1440px、スマートフォン390pxを初期の検証幅にし、320pxと文字拡大でも確認する。
ブラウザーで主要画面と密度の高い章を開き、スクリーンショットを実際に見る。
ページの横はみ出し、図の折り返し、固定ヘッダーとの重なり、コントラスト、フォーカスを確認する。
検証幅・対象ページ・操作・エラーの有無を記録する。

### 検証状況の報告

静的検査／ビルド／ローカル表示／モック／SDK実行／実API／デプロイ／公開URLの表示を分ける。
未実施は未実施と書く。テストの成功だけで記事の事実やAPI精度を保証しない。

## GitHub Pagesで公開する場合

公開が依頼されているときだけ行う。
対象リポジトリ、ブランチ、公開範囲、既存ファイルを確認する。
GitHub Actionsのバージョンや設定は、その作業時点の公式資料で確認する。

- ユーザーサイトかプロジェクトサイトかを判別し、サブパスとアセットURLを合わせる。
- リポジトリのSettings → Pages → SourceをGitHub Actionsにする。
- 既存ワークフローがあるなら、JekyllやStatic HTMLのテンプレートを重複追加しない。
- `configure-pages`の404では、Pages未有効・公開元・認証権限を確認する。
- `enablement: true`を万能修正として追加しない。必要な権限と実際の設定を確認する。
- 最新HEADを読み、競合を解消して通常のcommitで反映する。force pushは使わない。
- Actionsの成功後、公開URLと主要アセット・深いページを開いて別途確認する。

公開設定を操作する権限がない場合は、できない設定名と必要な操作だけを案内する。
同じ失敗ログだけで再実行を何度も求めず、設定画面またはAPIで原因を確認する。
